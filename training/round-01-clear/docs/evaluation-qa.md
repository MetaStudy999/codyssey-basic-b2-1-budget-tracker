# B2-1 R01 — Evaluation Q&A Reference

실제 평가에서는 아래 내용을 외우기보다 본인의 코드와 Runtime 결과를 근거로 설명합니다.

## 1. 왜 JSONL을 내부 저장 포맷으로 선택했는가?

JSONL은 한 줄에 하나의 JSON 객체를 저장하므로 거래를 append하거나 한 줄씩 읽는 구조가 단순합니다. `tags`처럼 배열 형태의 필드도 CSV보다 자연스럽게 보존할 수 있고 Python 표준 `json` 모듈만으로 처리할 수 있습니다. 반면 update/delete와 복잡한 조회는 파일 전체 재작성/순회가 필요하므로 대규모 데이터에는 DB가 더 적합합니다.

## 2. 모듈 책임은 어떻게 나눴는가?

- `models.py`: Transaction/Budget 등 데이터 구조
- `repositories.py`: JSONL 파일 I/O와 원자적 재작성
- `services.py`: 검증, 검색, 요약, 예산, 카테고리 같은 비즈니스 규칙
- `cli.py`: argparse, 사용자 입력과 출력
- `utils.py`: 공통 검증, decorator, JSONL streaming

CLI가 파일을 직접 고치지 않고 서비스→저장소로 내려가게 해 책임을 분리했습니다.

## 3. 최소 2개 클래스의 책임 경계는?

`TransactionRepository`는 거래 파일 저장/조회/재작성만 담당하고, `BudgetService`는 카테고리 존재 여부, 양수 금액, 월 요약 같은 업무 규칙을 담당합니다. 저장 방식과 업무 규칙을 분리하면 파일 포맷을 바꾸거나 규칙을 테스트하기 쉽습니다.

## 4. list/search를 제너레이터로 구현한 이유는?

모든 거래를 리스트로 메모리에 올리지 않고 한 레코드씩 처리할 수 있기 때문입니다. Reference는 JSONL 파일을 뒤에서 블록 단위로 읽는 `iter_jsonl_reverse()`를 사용해 **최신순과 스트리밍을 동시에** 만족시킵니다. `list --limit`은 필요한 N건을 읽으면 즉시 중단합니다.

## 5. 데코레이터는 무엇을 분리했는가?

`handle_cli_errors`가 CLI의 공통 예외 처리를 담당합니다. 각 기능이 매번 try/except와 오류 출력 형식을 반복하지 않고, 정상 로직에 집중하도록 했습니다. 사용자에게는 stacktrace 대신 `[오류] 원인`과 `[힌트]`를 보여 주고 오류 종료 코드 2를 반환합니다.

## 6. 타입 힌트는 어떤 이점이 있는가?

예를 들어 `add_transaction(..., amount: str | int) -> Transaction`은 입력과 반환 계약을 코드에서 바로 알 수 있게 합니다. `Generator[Transaction, None, None]`은 list/search가 전체 list가 아니라 스트리밍 generator임을 명확히 보여 줍니다. IDE/정적 분석과 코드 리뷰에서 잘못된 사용을 일찍 찾는 데 도움이 됩니다.

## 7. update/delete를 어떻게 안전하게 처리했는가?

기존 파일을 직접 잘라내지 않습니다. 같은 디렉터리에 임시 파일을 완전히 작성하고 `flush()`/`fsync()` 후 `os.replace()`로 교체합니다. 그래서 재작성 중 오류가 나더라도 기존 파일을 가능한 한 유지하고, 교체 시점은 원자적으로 처리합니다.

## 8. 카테고리를 사용 중일 때 왜 삭제를 막는가?

거래가 참조하는 카테고리를 먼저 삭제하면 저장 데이터가 유효하지 않은 상태가 됩니다. Reference는 해당 카테고리를 사용하는 거래를 먼저 찾아 삭제를 차단하고, 거래를 다른 카테고리로 update한 뒤 다시 삭제하도록 안내합니다.

## 9. import CSV에 깨진 행이 섞이면 어떻게 처리하는가?

Reference는 **부분 성공 + 명시적 리포트** 전략입니다. 각 행을 독립 검증해 정상 행은 저장하고 잘못된 행은 건너뛴 뒤 `imported`, `skipped`, 행 번호와 원인을 출력합니다. 사용자가 일부 실패를 모르고 전체 성공으로 오해하지 않도록 결과를 명확히 보여 줍니다. 전부 아니면 전무가 필요한 업무라면 전체 사전검증 후 일괄 commit/rollback 전략이 더 적합합니다.

## 10. 프로그램 재실행 후 데이터가 유지되는 이유는?

거래·카테고리·예산을 각각 JSONL 파일에 영구 저장하기 때문입니다. 서비스 객체가 종료되어도 파일이 남아 있고 다음 실행에서 Repository가 같은 파일을 다시 읽습니다.

## 11. 왜 transactions/categories/budgets를 세 파일로 나눴는가?

서로 다른 데이터의 역할과 생명주기가 다르기 때문입니다. 거래 이력, 허용 카테고리, 월 예산을 분리하면 각 파일의 구조가 단순해지고 한 종류의 변경이 다른 데이터를 불필요하게 다시 쓰는 것을 줄일 수 있습니다. 공식 요구사항의 3개 이상 영구 저장 파일도 충족합니다.

## 12. 거래가 10만 건이면 어디가 병목인가?

현재 구조에서는 `next_id()`가 전체 거래를 스캔하고, summary도 전체 순회하며, update/delete는 전체 파일을 재작성합니다. 규모가 커지면 SQLite/PostgreSQL 등 DB로 이동해 PK/인덱스를 사용하고, 월별 집계는 인덱스나 증분 집계를 적용할 수 있습니다. R01에서는 파일 I/O와 generator 원리를 학습하는 것이 우선입니다.

## 13. CSV를 내부 저장 대신 import/export에만 쓰는 이유는?

CSV는 외부 교환 형식으로 널리 쓰이고 스프레드시트와 호환성이 좋습니다. 반면 `tags`처럼 하나의 필드에 여러 값을 담을 때 escaping 규칙이 필요하고 내부 구조 확장에 불편할 수 있습니다. 그래서 내부는 JSONL, 외부 교환은 고정 CSV 스키마로 분리했습니다.

## 14. 오류 종료 코드가 왜 중요한가?

사람에게 오류 메시지를 보여 주는 것과 별개로 shell/script는 성공/실패를 숫자로 판단합니다. 정상은 0, 오류는 0이 아닌 값을 반환해야 이후 자동화나 테스트가 실패를 감지할 수 있습니다.
